Ask the app what's wrong

Well-built apps can report their own configuration. This one exposes a small diagnostic page at /api/health.

/api/health{ "keyConfigured": false }

keyConfigured: false tells us exactly where to look — the API key, not the app's code.

Open /api/health

Test the key by itself

Before touching any code, we can test the same credentials directly from a Windows command prompt.

set LTA_ACCOUNT_KEY=your_key curl.exe -4 -is -H "AccountKey: %LTA_ACCOUNT_KEY%" ^ "https://datamall2.mytransport.sg/ltaodataservice/CarParkAvailabilityv2"
HTTP/1.1 401 Unauthorized

401 means the server understood the request but rejected these exact credentials. The key itself is wrong.

Test the address by itself

Now the key is right, but the endpoint is mistyped.

curl.exe -4 -is -H "AccountKey: %LTA_ACCOUNT_KEY%" ^ "https://datamall2.mytransport.sg/ltaodataservice/CarParkAvailability"
HTTP/1.1 404 Not Found

Notice the missing v2. 404 means there's nothing to talk to at that address at all — a typo, not a credentials problem.

Get both right

With the real key and the correct endpoint, the same kind of request succeeds.

curl.exe -4 -is -H "AccountKey: %LTA_ACCOUNT_KEY%" ^ "https://datamall2.mytransport.sg/ltaodataservice/CarParkAvailabilityv2"
HTTP/1.1 200 OK

200 confirms both pieces are correct: valid key, valid address.

Confirm the fix

Once the correct key is saved as an environment variable in Vercel and the app is redeployed, the diagnostic changes too.

/api/health{ "keyConfigured": true }

Same endpoint, same app — just a different key behind it.

A quieter kind of risk

The app is fixed. Now let's look at something in the project's files that has nothing to do with curl or Vercel — how API keys are meant to be stored, and a small gap in how Git protects them.

Where the key is supposed to live

The project ships with a file called .env.example. It's a template, not a hiding place — it lists which key the app needs, without containing a real one.

.env.exampleLTA_ACCOUNT_KEY=your_key_here

When you actually configure the app — in Google AI Studio, in Vercel, or on your own laptop — you're meant to create a separate file, usually named .env, and put your real key there instead. That real .env file is the one meant to stay private.

View .env.example on GitHub

The safety net has a gap

Git decides what gets uploaded to GitHub using a file called .gitignore. Normally, it hides every .env file, since those can hold real secrets.

.gitignore.env* !.env.example

The line !.env.example is an exception — the ! means "don't hide this one." That's normally fine, since .env.example is only a template.

The risk is if a real key ever gets typed directly into .env.example instead of a proper .env file. Git was never hiding that file, so the real key would be pushed to GitHub and become public.

Rule of thumb Real keys go in .env. Placeholders go in .env.example. Keep the two separate.

What today's fix teaches

  • Check a health or status endpoint before touching code.
  • Test raw credentials with curl before blaming your own app.
  • 401 is a bad key. 404 is a bad address. 200 means both are correct.
  • Real secrets belong in .env, never in .env.example.
  • A leading ! in .gitignore means "don't ignore this" — read it carefully.
